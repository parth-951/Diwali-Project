### 3.1 Implementation notes that affect the results

- **Scalar (TC01):** rank-0 tensors are supported: `FloatTensor(std::vector<std::size_t>{}, 5.0f)`.
- **Creating from data (TC02-TC05):** MiniTensor has no constructor that takes values, so the values are written into the contiguous buffer after construction.
- **Zero initialization (TC06):** the constructor's `initial_value` defaults to 0, so initialization is part of the API contract.
- **Negative index (TC15):** The API takes unsigned std::size_t indices, so a literal T(-1,0) does not compile. A signed -1 converted at run time becomes SIZE_MAX and is rejected by the bounds check. Tensor unchanged verified
- **Reshape (TC39-TC45, PB12):** reshape works in place: only the shape metadata changes, and the element buffer is shared, not copied (the data pointer is the same before and after). An invalid reshape throws `std::invalid_argument` and leaves the tensor unchanged (TC43).
- **Errors:** invalid shapes throw `std::invalid_argument`; out-of-range indices throw `std::out_of_range`; impossible sizes throw `std::overflow_error`. Each error test checks that the exception was thrown and, where relevant, that the input tensor is unchanged.

### 3.2 TC35: error in the specification

The specification's expected values do not match its stated inputs: A{2,5}=1..10 times B{5,4}=1..20 (row-major) is [[175,190,205,220],[400,440,480,520]] (e.g. C(0,0) = 1*1+2*5+3*9+4*13+5*17 = 175), confirmed with NumPy float32. MiniTensor's output equals that product exactly.

MiniTensor's output: shape {2,4}; values [175,190,205,220,400,440,480,520]. The test is recorded as FAIL because the specification says its expected values are authoritative; the values were not changed. Please review the expected result for TC35.

## 5. Performance benchmarks

### 5.1 Protocol

- float32 everywhere. Inputs are created and initialized before timing; outputs are validated and checksummed after timing, outside the timed region.
- 5 untimed warm-ups, then 30 timed executions on a monotonic clock.
- Every configuration was run in **3 independent processes**. The runs were interleaved (all configurations once, then again, then a third time) so that drift affects every library alike.
- **Median** below is the overall median: the median of the three run medians. Minimum, mean and standard deviation are over all 90 timed samples.
- **Speedup** = reference median / MiniTensor median (above 1 means MiniTensor is faster). The main reference is Eigen 5.0.1 built with the same compiler and flags, as the specification's fairness notes recommend; NumPy 2.4.6 is shown as a second reference.
- All single-thread runs used `OMP_NUM_THREADS=1` and `OPENBLAS_NUM_THREADS=1`. Multi-thread runs (section 5.5) are compared only with MiniTensor's own 1-thread run.

## 6. Observations

- **Correctness:** every benchmark output was correct in every run for all three libraries (34 of 34 MiniTensor configurations, 26 Eigen and 26 NumPy configurations).
- **Against Eigen:** MiniTensor was faster in 1 of 26 single-thread configurations (PB03 4000x4000, by 3%).
  PB03: the difference is smaller than the spread between MiniTensor's own three run medians, so it is not a meaningful win.
- **PB04 caveat:** both drivers time the same loop over the contiguous buffer (`data()` with a float64 accumulator), yet the medians differ (1.298 ms against 0.6430 ms). Because the measured code is identical, this difference comes from how the two test programs were compiled, not from either library's storage.
- **PB05:** MiniTensor's run medians varied from 3.575 to 6.713 ms. Each `t({row, col})` read builds a temporary index vector (a heap allocation) and checks bounds, while Eigen's `t(row, col)` does neither in a release build. How much of the gap each part causes has not been profiled.
- **Small element-wise operations:** at 100x100, MiniTensor's addition takes 0.0113 ms against Eigen's 0.0009 ms. MiniTensor zero-fills each new output tensor before writing the results; the cause of the rest of the gap has not been profiled.
- **Matrix multiplication:** single-threaded PB11 reaches 24.4 GFLOP/s (Eigen 33.7, NumPy 113.9). With 8 OpenMP threads MiniTensor reaches 102.2 GFLOP/s, 3.98x its 1-thread speed.
- **Reshape semantics differ:** MiniTensor reshapes in place (metadata change, about 79 ns per call); Eigen's `Map` and NumPy's `reshape` create views. The specification asks for unlike semantics to be reported separately, so the PB12 speedup should be read with that in mind.
- **Timer resolution:** PB01 and the smallest element-wise sizes take around a microsecond, close to the 100 ns timer resolution, so their relative comparisons are less precise than the larger sizes'.

## 7. Deviations and limitations

- **Platform:** measured on Windows 11 on a laptop (AC power, Balanced power plan), not a dedicated Linux machine. The specification asks the evaluator to use one machine and power mode for every team, so these timings are for this machine only.
- **NumPy PB04 and PB05:** Python cannot loop over a million elements at C speed, so NumPy uses its vectorized equivalents (`sum` and fancy indexing over the same index list).
- **PB12 batching:** one reshape call is close to the timer resolution, so each timed sample is a batch of 1000 reshape calls, identical for all three libraries, as section 5 allows.
- **Team details:** the Team_ID is set to "MiniTensor". Replace it with the assigned team number or name if different.
